# LLM Coding Discipline

## Core Loop

Apply this skill as a process guardrail, not as a replacement for repository-specific instructions.

1. Define completion before editing.
   - Restate the concrete success criteria when the task is non-trivial, ambiguous, risky, or multi-step.
   - Convert vague asks into verifiable behavior. For example, "add validation" becomes the exact inputs rejected, user-visible result, and tests or smoke checks that prove it.
   - Ask only when the missing answer cannot be discovered locally and a reasonable assumption would be risky.
2. Read before writing.
   - Inspect the files, tests, imports, config, and nearby patterns that the change will touch.
   - Reuse existing project style, helper APIs, and dependency choices.
   - Search for similar implementations before adding new structure.
3. Plan only as much as the task needs.
   - For multi-step work, make an inspectable plan with evidence expectations.
   - For small clear fixes, proceed directly after reading enough context.
   - Keep explicit non-goals for risky, broad, or tempting cleanup work.
4. Make the smallest useful change.
   - Keep diffs proportional to the request.
   - Do not reformat, rename, reorganize, or upgrade unrelated code while passing through.
   - Be able to tie every changed line to the user request, a failing test, or a necessary local contract.
5. Verify with behavior.
   - Prefer reproducing a bug before fixing it.
   - Add or run tests that cover user-visible behavior, not just field assignments or happy-path construction.
   - If a behavior cannot be tested cheaply, run the strongest available smoke or static check and state the residual risk.
6. Review before reporting done.
   - Inspect the final diff for accidental broadening, style drift, dependency creep, secrets, and missing evidence.
   - Compare the result against the original success criteria.
   - Report what changed, why, what verified it, and any remaining risk.

## Debugging Rules

- Investigate instead of guessing.
- Read the complete error, stack trace, logs, request, response, and reproduction path before changing code.
- Change one causal thing at a time when isolating a failure.
- Do not hide unexpected nulls, missing fields, 500s, flakes, or race conditions with broad fallbacks until the cause is understood.
- When repeated fixes fail, stop and re-check the premise rather than layering more patches.

## Dependency Rules

- Treat each new dependency as permanent code outside local control.
- Before adding one, check whether the standard library, existing project dependencies, or local helpers already solve the problem.
- If a dependency is still warranted, make the reason visible in the implementation notes or final response.
- Verify lockfile or package-manager changes when dependency manifests are touched.

## Common Failure Modes

Stop and narrow the work if one of these appears:

- Kitchen Sink: a small task starts restructuring unrelated areas.
- Wrong Abstraction: abstraction appears before repeated real use or before the codebase pattern supports it.
- Optimistic Path: only happy-path behavior works while user input, network, server, empty-state, and permission failures are ignored.
- Runaway Refactor: one fix cascades through files without a clear requirement.
- Knowledge Hallucination: code uses an API, parameter, CLI flag, or library behavior not verified from local source or current docs.
- Format Fog: formatting churn makes the meaningful diff hard to review.

    32	                                                    tinguished by the property that for any splitting at least one partial trace is maximally mixed. Due
    33	                                                    to maximal possible correlations between any two selected subsystems these states have numerous
    34	                                                    applications in various fields of quantum information processing including multi-user teleportation,
    35	                                                    quantum error correction and secret sharing. We present an updated survey of various techniques
    36	                                                    to generate such strongly entangled states, including those going beyond the standard construction
    37	                                                    of graph and stabilizer states. Our contribution includes, in particular, analysis of the degree of
    38	                                                    entanglement of reduced states obtained by partial trace of AME projectors, states obtained by
    39	                                                    a symmetric superposition of GHZ states, an orthogonal frequency square representation of the
    40	                                                    “golden” AME state and an updated summary of the number of local unitary equivalence classes.
