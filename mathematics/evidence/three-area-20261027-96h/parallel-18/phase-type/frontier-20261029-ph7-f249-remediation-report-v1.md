## 2. Threat model and conditional trust boundary

Threats addressed in the design include an arbitrary caller fabricating a GO and its matching self-hash; mutable workspace/PYTHONPATH/sitecustomize contamination; substitution of an entrypoint after an initial file read; and an orphan, incomplete or mismatched success-looking result/receipt. An attacker allowed to control BOTH the alleged parent policy trust anchor and the GO, or the trusted supervisor, OS/kernel, read-only mount enforcement, native runtime, or interpreter before prelude execution, is **outside the assumed boundary**. Under that attacker model no in-process hash check can authenticate its own startup. If parent and GO writer share the same mutable authority without an independent anchor, this design does NOT authenticate parent issuance.

A prospective parent supervisor must independently freeze and bind, BEFORE Python starts: actual `-I -S -c` prelude bytes and argv, launcher bytes, the parent-controlled policy SHA through a genuinely independent channel, the interpreter and stdlib/import paths, read-only snapshot mount, and actual native/dynamic-runtime images. The admitted policy binds a single GO hash, source snapshot manifest, entrypoint hash and native-supervisor attestation. The launcher requires no site/user hooks, all `sys.path` and loaded file-backed Python modules inside the pinned read-only snapshot, exact inventory/no unlisted or symlinked entries, and `statvfs` read-only flags on the snapshot and traversed submounts. The native-image receipt is a **parent assertion pinned by policy**, not proof that the launcher independently enumerated actual dyld images. An actual supervisor, OS-enforced read-only snapshot and trusted policy distribution are NOT yet provided or tested.
